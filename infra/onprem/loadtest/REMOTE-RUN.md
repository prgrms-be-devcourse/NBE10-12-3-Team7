# 다른 머신에서 부하를 걸 때 — 인계 문서

**부하 생성기(k6)를 앱 스택과 다른 머신에서 돌리는 절차다.** 이 문서만 보고 따라올 수 있게
맥락까지 적었다 — 이 대화에 없던 사람(또는 에이전트)이 읽는다는 전제다.

기록 규칙은 `results/README.md`, 회차 설계 배경은 각 회차의 `results/*/summary.md` 를 함께 볼 것.

---

## 왜 다른 머신인가

지금까지 5개 회차를 **맥 한 대에서** 돌렸다. k6 와 앱·MySQL 이 같은 10코어를 나눠 써서,
무릎이 나올 때마다 **"앱의 한계인가 부하 생성기의 한계인가"** 를 갈라야 했다.

| 회차 | 무릎 | 그때 VM CPU | 판정 |
|---|---|---|---|
| 읽기 · 필터 없음 | 없음(초당 600까지) | 61 % | 유효 |
| 읽기 · 동네 필터 | 초당 200~230 | 57 % | 유효 |
| 쓰기 · 등록 상한 | 초당 1,000~1,200 | 68 % | 유효 |

전부 CPU 90 %(폐기 기준) 아래에서 무릎이 나와 결론은 유효했지만, **그 CPU 에 k6 몫이
얼마나 섞였는지는 끝까지 몰랐다.** 부하 생성기를 분리하면 그 불확실성이 사라진다.

---

## 이 환경의 제약 — 반드시 먼저 읽을 것

**양쪽 노트북이 모두 Wi-Fi 다.** 이건 통제하지 못하는 변수를 하나 들여오는 것이다.

### 대역폭이 시나리오를 제한한다

Wi-Fi 는 반이중이고 공중을 공유한다. 기기 → AP → 기기로 가면 **프레임이 공중을 두 번**
지나므로 실효 처리량이 절반이 된다. 실측 전 추정으로 약 **4~5 MB/s** 다.

| 경로 | 응답 크기 | 초당 최대 요청(4.5 MB/s 기준) |
|---|---|---|
| `/` (랜딩) | 17.4 KB | **270** |
| `/api/products?size=30` | 9.4 KB | **490** |
| `/api/products?size=1` | 449 B | 10,509 |
| `/api/categories` | 334 B | 14,127 |

**랜딩 페이지(`/`) 시나리오는 이 환경에서 돌리지 말 것.** 초당 270 에서 네트워크가 벽인데
앱은 그보다 훨씬 위에 있어, 앱이 아니라 Wi-Fi 를 재게 된다.

### 변동성이 회차 비교를 깬다

유선은 고정된 벽이지만 Wi-Fi 는 **움직이는 벽**이다. 신호·간섭·다른 기기의 airtime 사용에
따라 실시간으로 바뀐다. 그래서:

- **회차 전후로 `iperf3` 를 재고 그 값을 기록한다.** 조건이 변했는지 판별할 유일한 방법이다
- 측정 중 같은 Wi-Fi 의 다른 기기 사용을 자제한다(영상·대용량 다운로드)
- 노트북을 AP 가까이 두고 5GHz 를 쓴다

## 첫 회차로 무엇을 할 것인가 — 2회차(동네 필터) 재현

**새 시나리오를 얹기 전에, 이미 잰 회차를 부하 생성기만 바꿔 다시 돌린다.**

| | 맥 로컬 2회차 | 이번 노트북 회차 |
|---|---|---|
| 시나리오 | 동네 필터 목록 | **동일** |
| 계단 | 초당 20 → 600 | **동일** |
| 앱 이미지·데이터·풀·요청 제한 | 고정 | **동일** |
| **바뀌는 것** | k6 가 앱과 같은 맥 | **k6 가 다른 노트북** |

이유가 넷이다.

1. **대역폭 안에 들어온다** — 무릎이 초당 200~230 인데 한계가 490 이다. 네트워크가 벽이
   되기 전에 앱 무릎을 볼 수 있다
2. **맥 로컬 결과와 직접 비교된다** — "CPU 격리가 결과를 얼마나 바꾸나"를 처음으로 정량화한다
3. **한 번에 하나만 바꾼다**는 이 프로젝트의 원칙에 맞는다
4. **노트북 환경 자체를 검증하는 회차**가 된다. 배선이 맞는지 확인한 뒤에 새 것을 얹는다

비교 대상: `results/2026-08-04-s01-arrival-region-filter/`

## 노트북 쪽 절차

### 1. 받기

```bash
git clone https://github.com/prgrms-be-devcourse/NBE10-12-3-Team7.git
cd NBE10-12-3-Team7 && git checkout fix/loadtest-run-prep
cd infra/onprem/loadtest
```

**도커만 있으면 된다.** k6 도 Node 도 설치할 필요가 없다.

### 2. `.env` 만들기

```bash
cp .env.example .env
```

세 값을 채운다(`.env` 는 gitignore 다):

| 키 | 값 |
|---|---|
| `BASE_URL` | `http://192.168.200.167` — 맥에서 `ipconfig getifaddr en0` 로 확인한 값 |
| `K6_PROMETHEUS_RW_SERVER_URL` | `http://192.168.200.167:9090/api/v1/write` |
| `LOGIN_PASSWORD` | 시드 계정 비밀번호. **코드·문서에 적지 않는다** — 맥 담당자에게 별도로 받는다 |

`LOGIN_PASSWORD` 는 로그인 회차(`LOGIN=true`)에서만 필요하다. 첫 회차(동네 필터)는 비로그인이라
비워둬도 된다.

### 3. 도달 확인

```bash
ping -c 3 192.168.200.167
curl -s -o /dev/null -w '%{http_code}\n' "http://192.168.200.167/api/products?size=1"   # 200 이어야 한다
```

### 4. 대역폭 측정 — **회차 전 필수**

맥에서 iperf3 서버를 띄운 상태로(맥 담당자가 실행):

```bash
docker run --rm -p 5201:5201 networkstatic/iperf3 -s
```

노트북에서 **응답이 흐르는 방향**(맥 → 노트북)을 잰다. `-R` 이 그 방향이다:

```bash
docker run --rm networkstatic/iperf3 -c 192.168.200.167 -R -t 20
```

**`Bitrate` 값을 기록한다.** 이 값이 회차의 대역폭 상한이고, 계단 판정의 근거가 된다.

```
초당 최대 요청 = 실효 처리량(B/s) ÷ 9,628 B      # 동네 필터 응답 크기
```

### 5. 배선 확인 (기록 안 남김)

```bash
docker compose run --rm k6 run /scripts/s00-ratelimit.js
```

요청 제한이 해제돼 있으므로 **429 가 0** 이어야 한다. 429 가 나오면 맥 쪽 `RATE_LIMIT_CAPACITY`
가 되돌아간 것이다(위 참고).

```bash
SMOKE=true REGION_CODE=1111010100 ./scenarios/run.sh s01-arrival wiring
```

35초짜리다. 통과하면 폴더를 지운다 — **SMOKE 는 기록에 남기지 않는다.**

```bash
rm -rf results/$(date +%Y-%m-%d)-s01-arrival-wiring
```

### 6. 본 회차 (15분 30초)

```bash
REGION_CODE=1111010100 ./scenarios/run.sh s01-arrival laptop-region-filter
```

`run.sh` 가 온프렘 네트워크가 없는 것을 감지해 **오버레이를 자동으로 빼고** `.env` 의 LAN IP 를
쓴다. 별도 플래그가 필요 없다.

무릎을 확실히 넘으면(배수 10배) 자동 중단된다.

## 판정 — 무엇이 벽인지 가르는 법

이 환경에서는 벽이 셋 중 하나다. **구분하지 못하면 기록할 수 없다.**

| 관측 | 결론 | 조치 |
|---|---|---|
| Grafana ③행 네트워크가 **iperf3 실측치에 붙음** + 응답 느려짐 | **Wi-Fi 가 벽** | 그 구간 폐기. 시나리오를 작은 응답으로 바꾼다 |
| `hikaricp_connections_pending` 이 0 → 급증, `active` 가 10 고정 | **앱(커넥션 풀)이 벽** | 찾는 것. 맥 로컬 2회차와 같은 서명 |
| `dropped_iterations` 오르는데 네트워크·pending 둘 다 여유 | **노트북 k6 가 벽** | 노트북 CPU 확인. `PRE_VUS`·`MAX_VUS` 조정 |

Grafana 는 맥의 `http://192.168.200.167:3001` 에서 본다. 회차는 상단 `testid` 로 고르고,
값은 결과 폴더 이름과 같다.

- 앱·DB 지표: **온프레미스 종합** 대시보드
- 네트워크·nginx 지표: **트래픽 부하 — 웹 진입 계층** 대시보드

## 기록 — 구멍이 하나 있다

`run.sh` 는 회차마다 `conditions.md` 를 자동으로 채우지만, **노트북에는 스택이 없어
앱 이미지·커넥션 풀·데이터 건수를 수집하지 못한다.** `"이 머신에 스택이 없어 수집하지
않았다"` 만 적힌다.

→ **회차 직전에 맥에서** 아래를 실행하고, 출력을 회차 폴더의 `conditions.md` 에 붙인다:

```bash
cd infra/onprem/loadtest && ./setup/stack-conditions.sh
```

이게 없으면 나중에 그 회차가 **어떤 앱 이미지·풀 크기·데이터 크기에서 잰 것인지 판별할 수
없다.** 이 프로젝트에서 가장 위험한 실패는 조용히 조건이 어긋난 숫자가 표에 남는 것이다.

### 회차 조건에 추가로 남길 것 (Wi-Fi 라서 생긴 항목)

- 노트북의 Wi-Fi 링크 속도와 AP 와의 거리·채널
- **회차 전후 `iperf3` 실효 처리량** — 조건이 변했는지 판별하는 유일한 값
- 맥의 IP (DHCP 로 바뀐다)

### 결과 전달

회차 폴더(`results/<날짜>-<시나리오>-<메모>/`)를 커밋해 push 한다. `raw/` 는 gitignore 라
자동으로 빠진다. `summary.md` 의 "그래서 무엇을 알게 됐는가" 는 **사람이 채운다** —
비워두면 나중에 그 회차를 읽을 수 없다.

## 하지 말 것

- **랜딩 페이지(`/`) 시나리오** — 이 환경에서는 네트워크만 재게 된다
- **맥에서 다른 부하를 동시에 돌리는 것** — 두 부하테스트가 겹치면 둘 다 무효다
- **측정 중 develop 브랜치에 push** — Jenkins 가 2분마다 폴링해 빌드가 돌면 그 회차가 오염된다
- **회차 도중 조건 변경** — 앱 재기동·데이터 적재·설정 변경은 회차를 나눠서 한다
- **SMOKE 회차를 기록에 남기는 것** — 확인 후 폴더째 지운다
