# 회차 요약 — s01-arrival / baseline (1회차)

조건은 옆의 `conditions.md` 에 자동으로 남아 있다. 여기는 **그래서 무엇을 알게 됐는가**를 쓴다.

## 무엇을 확인하려고 돌렸나

비로그인 사용자가 상품 목록 화면에 들어오기만 할 때 **초당 몇 명까지 버티나** — 이 서비스의
상한. 이후 회차(동네 필터·상세 진입·로그인)가 이 값을 얼마나 깎는지 비교할 기준선이다.

## 결과 — 무릎이 나오지 않았다

| 항목 | 값 |
|---|---|
| 이 회차 무부하 기준선 | **8.5 ms** (`setup()` 실측, 20건 중앙값) |
| 배수 p95 | **1.17 배** ← 판정. 허용선 3 배 |
| 배수 p99 | 2.12 배 |
| 목록 응답 p95 · p99 | 9.9 ms · 18.0 ms |
| 실패율 | 0.00 % |

| 버린 반복 (`dropped_iterations`) | **0** |

**계단 최상단인 초당 600 진입(= 요청 1,200건/초)까지 전부 소화했다.** 실패도 드롭도 없다.

## 무릎

**이 계단에서는 안 꺾였다.** 그것도 결과다.

**무엇이 먼저 포화됐나:** 아무것도 포화되지 않았다.

- **커넥션 풀 아님** — `pending` 이 전 구간 0, `active` 최대 6/10
- **DB 아님** — 버퍼풀 히트율 100.000 %, 디스크를 전혀 타지 않았다
- **가장 먼저 차오른 것은 VM CPU** — 600 진입에서 61 %. 다만 이 CPU 는 **앱과 k6 가 나눠
  쓰는 값**이라 "앱이 61 % 를 썼다"는 뜻이 아니다

**이론 상한 계산이 틀렸다.** 계단 설계 때 "무부하 12ms × 커넥션 10 → 초당 833 요청"으로 잡고
무릎을 초당 125~200 진입으로 예상했는데, 실제로는 1,200 요청/초를 여유롭게 처리했다.
무부하가 12ms 가 아니라 **8.5ms** 였고, 쿼리가 전부 버퍼풀 히트라 커넥션 하나가 훨씬 많은
요청을 돌렸다.

## 이 숫자가 낙관적인 이유 (반드시 함께 읽을 것)

- **항상 같은 첫 페이지 30건만 조회했다.** `cursor` 도 `regionCodes` 도 붙지 않는다.
  10만 건 중 같은 페이지만 반복해 읽으니 **버퍼풀이 가장 잘 듣는 조건**이다
- 로그인·동네 필터·상세 진입·스크롤이 전부 빠져 있다
- 부하 생성기와 서버가 **같은 맥 한 대**를 나눠 쓴다. VM CPU 61 % 에는 k6 몫이 포함돼 있어,
  계단을 더 올리면 앱보다 부하 생성기가 먼저 한계에 닿을 수 있다

**즉 "잘 봐줘야 이만큼"이다.** 실사용에 가까운 조건일수록 숫자는 내려간다.

## 버린 구간

없음. `dropped_iterations` 0, VM CPU 최대 61 % 로 폐기 기준(90 %)에 닿지 않았다.

## 이번 회차에서 나온 발견

**상품 목록에 N+1 이 있다 → `perf/FINDINGS.md` 의 F-05 로 등록했다.**

| 요청 | 쿼리 |
|---|---|
| `?size=1` | 10 |
| `?size=10` | 19 |
| `?size=30` | **33** |

부하 중 비율도 계단 전체에서 일정했다(요청당 18.5건). **응답시간에는 전혀 드러나지 않았다** —
버퍼풀 히트율이 100 % 라 33개 쿼리가 각각 0.1ms 수준이었기 때문이다. F-01(동네 필터 26.7배)이
버퍼풀 히트율 하락과 같은 구간에서 터진 것과 같은 뿌리일 가능성이 있다.

## 측정 결함 (이 회차에 발견, 이후 회차부터 수정됨)

k6 가 트렌드 분위수를 **테스트 시작부터 누적한 게이지**로 보냈다. 15분 내내 배수 p95 가
2.57 → 1.17 로 단조 감소했고, 마지막 값이 요약의 전체 합산값과 정확히 같았다.
**계단별 무릎 위치를 시간축에서 읽을 수 없는 상태였다.**

이번 회차는 무릎 자체가 없어 결론이 바뀌지 않는다. 다음 회차부터는 네이티브 히스토그램으로
전송해 구간별 분위수를 계산한다(커밋 `3114544`).
