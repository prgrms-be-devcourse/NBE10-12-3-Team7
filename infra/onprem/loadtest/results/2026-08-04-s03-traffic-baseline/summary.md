# 회차 요약 — s03-traffic / baseline (복합 트래픽, **CPU 워처로 중단**)

조건은 옆의 `conditions.md` 에 자동으로 남아 있다. 여기는 **그래서 무엇을 알게 됐는가**를 쓴다.

## 무엇을 확인하려고 돌렸나

지금까지는 경로를 하나씩 격리해서 쟀다. 이 회차는 반대로 **실제 사용자 구성에 가깝게 섞어
총 상한**을 잰다. 격리 측정을 먼저 끝냈기 때문에 섞였을 때 나온 숫자를 분해할 수 있다.

구성(스크립트 상단 주석 참고 — **실측이 아니라 우리가 정한 모델**이다):
비로그인 목록 30% · 로그인 목록(동네 필터 `1111010100`) 30% · 상세 40%

## 결과 — 무릎을 찾았다. 초당 400 진입 = 약 1,200 요청/초

| 항목 | 값 |
|---|---|
| 무부하 기준선 | 비로그인 7.1 ms · 로그인+동네 17.9 ms · 상세 5.4 ms |
| **무릎** | **초당 약 400 화면 진입 = 약 1,200 요청/초** |

| 무릎 직후 배수 p95 | **20.11 배** (pending 74, active 10 고정, CPU 75%) |
| 종료 | **VM CPU 70% 워처로 중단** (배수 임계보다 CPU 가 먼저 걸렸다) |

## 무엇이 먼저 포화됐나 — 커넥션 풀 (네 번째 관측)

`pending` 0 → 74, `active` 가 **풀 최대(10)에 붙었다.** 읽기·쓰기 격리 회차와 **같은 실패 서명**이다.

| 회차 | 무릎 | 무릎 시점 pending / active |
|---|---|---|
| 읽기 · 동네 필터 | 초당 200~230 진입 | 0 → 187 / 10 고정 |
| 쓰기 · 등록 | 초당 1,000~1,200 | 0 → 186 / 10 고정 |
| **복합 (이 회차)** | **초당 400 진입** | **0 → 74 / 10 고정** |

## 이 회차의 핵심 — 경로별 상한은 더할 수 없다

무릎 시점에 각 경로가 실제로 받고 있던 부하:

| 경로 | 이 회차에서 | 단독 무릎 | 비고 |
|---|---|---|---|
| 비로그인 목록 | 120/초 | 없음(600+) | 여유 |
| **로그인 목록(동네)** | **120/초** | **200~230** | **단독 무릎의 절반뿐** |
| 상세 | 160/초 | 미측정 | |

**가장 약한 경로가 자기 한계의 절반만 받고 있는데도 시스템이 무너졌다.**
커넥션 풀이 **공유 자원**이라 세 경로가 합쳐서 마르게 만들기 때문이다.

→ **"각 경로 상한을 재고 더하면 전체 상한"이라는 계산은 성립하지 않는다.**
복합 회차를 따로 돌려야 하는 이유가 이것이다.

## 종료 사유 — 무릎이 아니라 CPU 워처였다

이 회차부터 "VM CPU 70% 연속 초과 시 중단" 을 넣었고, 그것이 먼저 걸렸다(CPU 75%).
**다만 무릎은 그 직전에 이미 관측됐으므로 결론은 유효하다.**

### 그런데 임계값 70% 는 너무 보수적이었다 — 실측으로 확인됨

이 회차에서 처음으로 `docker stats` 를 샘플링해 **컨테이너별 CPU 를 분리**했다:

| 시각 | 전체 VM | **k6** | 앱 | MySQL |
|---|---|---|---|---|
| 초당 100 진입 | 25.8 % | **1.4 %** | 8.9 % | 13.2 % |
| 초당 400 진입 | 57.3 % | **3.0 %** | 19.2 % | **30.7 %** |

**k6 는 전체의 3% 밖에 쓰지 않는다.** 지금까지 모든 회차 요약에 "이 CPU 에는 k6 몫이
섞여 있다" 는 단서를 달았는데 — **그 단서가 사실상 무의미했다.**

그리고 **CPU 를 가장 많이 쓰는 것은 MySQL(30.7%)** 로 앱(19.2%)의 1.6배다.
F-05(요청당 33 쿼리)가 여기서도 드러난다 — 쿼리를 많이 만들수록 DB 가 CPU 를 먹는다.

→ k6 몫이 3% 이므로 70% 캡은 앱을 보호한 것이 아니라 **측정을 일찍 끊은 것**에 가깝다.
다음 회차부터 **85%** 로 올렸다(폐기 기준 90% 바로 아래).

## 이 회차에서 잃은 것

- **k6 요약 JSON 이 없다.** 워처가 k6 를 강제 종료해 `handleSummary` 가 돌지 않았다.
  위 숫자는 전부 Prometheus 시계열에서 복원한 것이다.
- **경로별 배수를 못 읽었다.** 그 값은 k6 요약 JSON 의 서브메트릭에만 있고
  (Prometheus 로는 안 넘어간다), JSON 이 없으므로 "어느 경로가 먼저 무너졌나" 를
  이 회차에서는 확인할 수 없다. SMOKE 에서는 정상적으로 출력됐다.
- `run.sh` 가 k6 종료 후에도 끝나지 않고 매달렸다. 백그라운드 워처·샘플러가 파이프를
  잡고 있어서였다 — 다음 회차 전에 고쳤다.

## 버린 구간

**초당 396 진입 이후(붕괴 구간).** VM CPU 75% 로 폐기 기준(90%)에는 닿지 않았으나
워처가 중단시켜 데이터가 짧다. 무릎 지점(초당 400, CPU 62%)은 **유효하다.**

## 결론 — 현재 설정에서 이 서비스가 받는 트래픽

> **초당 약 1,200 요청 (화면 진입 초당 400명).**
> think time 4초를 가정하면 동시 접속 약 1,600명에 해당한다(이 환산은 가정에 의존한다).
>
> **상한을 정한 것은 CPU·메모리·디스크가 아니라 DB 커넥션 풀(10)이다.**
> 이는 하드웨어 한계가 아니라 **설정과 쿼리 구조의 문제**이며, 둘 다 고칠 수 있다.

## 다음 회차의 목적

1. **커넥션 풀 확대 후 이 회차 재실행.** 복합 시나리오가 실사용에 가장 가까우므로
   "고쳤을 때 상한이 얼마나 오르나" 를 가장 잘 보여준다. 미완으로 남은 검증이다.
2. **F-05(목록 N+1) 처방 후 재실행.** MySQL 이 CPU 1위라는 것이 이 회차에서 확인됐다.
3. `POLL=true` 로 알림 폴링 배경부하를 얹은 회차 — 상시 트래픽이 깔린 상태의 상한.
