# 회차 요약 — s03-throughput-ceiling / laptop-min-response

조건은 옆의 `conditions.md` 에 자동으로 남아 있다. 여기는 **그래서 무엇을 알게 됐는가**를 쓴다.

## 무엇을 확인하려고 돌렸나

동네필터(9.6KB)는 이 Wi-Fi(iperf3 실측 1.91MB/s)에서 대역폭 상한이 초당 198건이라 앱 무릎
(200~230)과 겹쳐 앱을 못 잰다. **응답을 449B(size=1)로 줄여 대역폭 상한을 초당 4,259건으로
올린 뒤, 네트워크가 아니라 앱(nginx·Tomcat·커넥션풀)이 먼저 무너지는 지점을 보려고** 돌렸다.

## 무릎

**초당 500~1000 사이. 지속 가능 상한 ~700 req/s, 순간 최대 전달 ~850 req/s.**

**무엇이 먼저 포화됐나:** **네트워크(Wi-Fi)** — 앱이 아니다.
**근거:**
- 1000 계단에서 **앱은 856 req/s 를 서버측 30ms 로 처리**했는데 **클라이언트는 p99 840ms** 를
  봤다 — 810ms 격차가 전부 네트워크 경로에서 났다. 앱 내부 지연은 회차 내내 30ms 로 평평했다.
- 856 req/s × 449B = **0.38 MB/s = 대역폭(1.91)의 20%.** 대역폭 벽이 아니라 **Wi-Fi airtime +
  연결 폭주**(k6 VU 8→1087개 동시 TCP)가 벽이다. 마지막 HTTP 0 도 그 연결 실패다.
- **부수 발견(앱의 다음 병목):** 커넥션 풀 10개가 ~800 req/s 부터 큐잉 시작(`pending` 최대 16,
  `acquire` 최대 24ms). **단 `timeout_total`=0 으로 버텼다** — 치명타는 네트워크에 먼저 왔고,
  풀은 아직 무릎이 아니다. 원 가설(풀 10개 병목)의 첫 신호는 잡았다.

## 버린 구간

1000 계단(≈5m 이후) 전체. `dropped_iterations` 1,594 + VU 폭주 + HTTP 0 는 앱이 아니라
**노트북↔맥 Wi-Fi 경로**를 잰 것이라 앱 상한 판정에 쓰지 않는다.

## 다음 회차의 목적

**이 Wi-Fi 는 작은 응답으로도 ~850 req/s 에서 먼저 막는다(앱은 아직 30ms 여유).** 앱의 진짜
상한을 보려면 네트워크를 걷어내야 한다 — **① 유선 이더넷 연결 후 s03 재실행**(airtime/지연 벽
제거 → 풀 10개 무릎이 다음으로 드러날 것), 또는 ② 500→600→700→800 촘촘한 계단으로 Wi-Fi
꺾임점과 풀 큐잉 시작점을 정밀 재측정. `DB_POOL_MAX=20` 확대 검증은 유선 회차 이후로 미룬다.
