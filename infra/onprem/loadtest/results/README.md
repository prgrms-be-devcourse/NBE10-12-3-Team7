# results — 회차 기록

`./scenarios/run.sh <시나리오> <메모>` 가 회차마다 폴더를 만든다. 직접 만들지 않는다.

```
2026-08-04-s01-arrival-baseline/
├── conditions.md              측정 조건. **스크립트가 자동으로 채운다 — 손대지 않는다**
├── summary.md                 결론. 사람이 채운다
├── s01-arrival-summary.json   k6 원시 측정값
└── raw/                       k6 원시 출력 (gitignore)
```

폴더 이름은 `<날짜>-<시나리오>-<메모>` 다. 하루에 여러 회차를 돌리므로 번호가 아니라
**조건이 이름에 보이게** 한다 — `2026-08-04-s01-arrival-region-filter` 처럼.

## 왜 conditions.md 를 자동으로 채우는가

숫자만 남으면 **그 숫자가 무엇의 결과인지 나중에 판별할 수 없다.** 그런데 조건을 손으로
적으면 반드시 빠뜨린다. 그래서 실행 직전에 실제 값을 읽어 남긴다:

측정 위치(맥 로컬 / LAN) · BASE_URL · 앱 이미지 빌드 시각 · 요청 제한값 · `[load]` 데이터 건수 ·
MySQL buffer pool · VM CPU·메모리 · 배경 컨테이너 목록 · 스크립트 git 리비전

**이 중 하나라도 다르면 다른 회차와 절대 수치를 비교할 수 없다.**

## summary.md 에 담을 것

`TEMPLATE-run.md` 를 복사해 쓴다(`run.sh` 가 자동으로 넣어준다).

- **판정은 무부하 대비 배수**로 적는다. 절대 ms 는 참고로만 — 측정 경로가 바뀌면 같은 앱이어도
  무부하가 달라진다(호스트 16.9ms / 컨테이너 23.9ms / LAN 25.6ms 로 실측됨)
- **무릎이 초당 몇 진입에서 생겼는지**를 적는다. k6 요약은 계단 전체의 합산값이라 여기에
  답하지 못한다 — Grafana 시간축에서 읽어야 한다
- **버린 구간을 반드시 적는다.** `dropped_iterations` 가 0 이 아니거나 VM CPU 가 90% 를
  넘은 구간은 앱이 아니라 부하 생성기·호스트를 잰 것이다
- 중간에 설정을 바꿨으면(제한값·버퍼풀·인덱스) **회차를 나눈다.** 조건이 다른 측정을 한 표에
  섞으면 표 전체가 무의미해진다

## 기록하지 않는 회차

`SMOKE=true` 로 돌린 것은 **배선 확인용**이라 기록에 남기지 않는다. 확인이 끝나면 폴더째
지운다. 35초짜리가 회차 목록에 섞이면 나중에 "이 숫자는 뭐지"가 된다.

## 왜 커밋하는가

"제한 해제 전후", "동네 필터 유무", "버퍼풀 확대 전후" 같은 비교는 **이전 회차가 남아 있어야**
성립한다. 요약과 조건만 커밋하고 원시 로그(`raw/`)는 제외해 리포가 무거워지는 것을 막는다.
