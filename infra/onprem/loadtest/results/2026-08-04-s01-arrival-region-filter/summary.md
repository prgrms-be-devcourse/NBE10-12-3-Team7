## 무엇을 확인하려고 돌렸나

1회차(필터 없음)와 **딱 하나만** 바꿔서 — 목록 조회에 `regionCodes` 를 붙여서 — 동네 필터가
동시성 상한을 얼마나 깎는지 본다. `perf/FINDINGS.md` 의 **F-01**(동네 필터가 20만 건부터
26.7배)은 데이터량 축에서 찾은 문제인데, 같은 문제가 **동시성 축에서도** 비용을 갖는지가 질문이다.

동네는 `1111010100`(서울 종로구 청운동, `[load]` 상품 **5,008건**). 이 데이터셋은 이봉형이라
12개 동네가 각 5,008건을 갖고 나머지 5,055개는 1~9건뿐이다. 큰 동네를 써야 "그 동네 상품 중
최신 30건"이 실제로 비싼 조회가 된다.

## 무릎

**초당 200~230 진입 사이.** 200 까지는 배수 1.4~1.6 으로 멀쩡했고, 400 으로 올라가는 램프
중간에서 한 구간 만에 12.4 배 → 190 배로 무너졌다.

**무엇이 먼저 포화됐나 — 커넥션 풀이다.**

무릎이 생긴 구간의 지표 순서가 근거다:

- `hikaricp_connections_pending` 이 **0 → 187** 로 튀었다
- `hikaricp_connections_active` 가 **10(풀 최대)에 붙어 내려오지 않았다**
- 같은 시점 **VM CPU 는 57 %** — CPU 가 원인이 아니다
- **버퍼풀 히트율 100.000 % 유지** — 디스크를 전혀 타지 않았다

`active` 만 봤으면 못 잡았다. 풀이 꽉 차도 active 는 상한에 붙어 있을 뿐이고, 실제로 밀리는지는
대기 큐에만 나타난다. 이 회차 직전에 종합 대시보드 ①행에 `pending` 을 추가한 것이 여기서 값을 했다.

## 버린 구간

**붕괴 이후(초당 400·600 계단) 전체.** 이유가 둘이다:

- **VM CPU 90 %** — 우리가 정한 폐기 기준(90 % 초과)에 닿았다. k6 가 VU 를 800개(maxVUs)까지
  늘려 붙잡고 있었으므로 이 CPU 에는 부하 생성기 몫이 크게 섞여 있다
- **`dropped_iterations` 72,543** — 목표 도착률을 채우지 못했다

**따라서 이 회차에서 방어할 수 있는 것은 "무릎의 위치와 원인"까지다.** 붕괴 후의 절대 배수
(193 배)나 응답시간(3.5 초)은 앱의 성능이 아니라 호스트 포화를 함께 잰 값이다.

무릎 지점(약 230 진입) 자체는 CPU 57 % 에서 관측됐으므로 **유효하다.**

## F-05 가설 수정 — 캐시가 아니라 커넥션이었다

F-05 등록 당시 "캐시 밖으로 나가면 N+1 이 33 번의 디스크 접근이 된다"를 가설로 적었다.
**이 회차에서는 버퍼풀 히트율이 100.000 % 를 유지한 채로 무너졌다.** 디스크는 원인이 아니었다.

쿼리 33 개가 전부 메모리 히트여도 그동안 **커넥션 하나를 계속 붙잡는다.** 동시성이 올라가면
풀(10개)이 마르고, 그때부터는 요청이 큐에서 기다린다. N+1 은 두 축에서 각각 다른 방식으로 비용을 낸다:

| 축 | 메커니즘 | 근거 |
|---|---|---|
| 데이터량 | 캐시 밖으로 나가면 디스크 33 번 | perf F-01 (히트율 하락과 상관) |
| **동시성** | **커넥션 점유 시간이 길어져 풀 고갈** | **이 회차 (히트율 100 % 유지, pending 187)** |

FINDINGS 의 F-05 를 이 실측으로 갱신했다.
