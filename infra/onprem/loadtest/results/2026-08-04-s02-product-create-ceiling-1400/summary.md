# 회차 요약 — s02-product-create / ceiling-1400 (쓰기 상한 탐색)

조건은 옆의 `conditions.md` 에 자동으로 남아 있다. 여기는 **그래서 무엇을 알게 됐는가**를 쓴다.

## 무엇을 확인하려고 돌렸나

쓰기 1회차가 초당 600 등록까지 무릎 없이 완주했다. **상한이 어디인지** 찾는다.
계단을 400 부터 1400 까지 올렸다(유지 30초). 1400 에서 멈춘 이유는 초당 600 에서 VM CPU 가
39% 였고 외삽하면 1400 근처가 90%(폐기 기준)라, 그 위로는 앱이 아니라 **호스트가 먼저 막힐
것으로 봤기 때문이다** — k6 가 같은 맥에서 돌기 때문이다.

## 결과 — 무릎을 찾았다. 그리고 벽은 호스트가 아니라 앱이었다

| 항목 | 값 |
|---|---|
| 무부하 기준선 | 3.9 ms (`setup()` 등록 20회) |
| **무릎** | **초당 1,000 ~ 1,200 등록** |
| 무릎 시점 VM CPU | **68 %** — 폐기 기준(90%)에 한참 못 미친다 |
| 배수 p95 (합산) | 13.87 배 — 붕괴 구간 포함이라 인용하지 않는다 |
| 실패율 | 0.00 % |
| 소화한 등록 | 737.8 건/초 평균 (총 264,235) |
| 버린 반복 | 710 (붕괴 이후 구간에 집중) |
| 종료 | **배수 10배 초과로 자동 중단** |

**예상이 빗나갔다.** 호스트 CPU 가 먼저 막힐 것으로 봤는데, **CPU 68% 에서 커넥션 풀이 먼저 말랐다.**
즉 이 회차가 찾은 것은 부하 생성기의 한계가 아니라 **앱의 쓰기 상한**이다.

## 무엇이 먼저 포화됐나 — 커넥션 풀

- `hikaricp_connections_pending` 이 **0 → 54 → 141 → 186**
- `hikaricp_connections_active` 가 **풀 최대(10)에 붙어 내려오지 않았다**
- **VM CPU 는 최대 68 %** — CPU 가 원인이 아니다
- **행 잠금 대기는 전 구간 0** — 락 경합도 아니다
- MySQL `threads_running` 최대 8, `max_connections` 151 — DB 쪽 여유는 충분했다

## 읽기와 같은 실패 모드다 — 커넥션 풀 가설이 두 번째 관측을 얻었다

| | 읽기(동네 필터, 2회차) | 쓰기(등록, 이 회차) |
|---|---|---|
| **무릎** | 초당 200~230 | **초당 1,000~1,200** |
| 무릎 시점 pending | 0 → 187 | **0 → 186** |
| 무릎 시점 active | **10 / 10** | **10 / 10** |
| 무릎 시점 VM CPU | 57 % | 68 % |
| 락 / 캐시 | 히트율 100 % | 락 대기 0 |
| **요청당 쿼리** | **18.5** (목록 단독 33) | **9.0** |

**두 시나리오가 독립적으로 같은 신호를 냈다** — pending 급증 + active 가 풀 최대 고정 + CPU 여유.
2회차만으로는 상관관계 하나였는데, 성격이 전혀 다른 부하에서 같은 서명이 나왔다.

**무릎 위치가 약 5배 차이나고, 그 방향이 요청당 쿼리 수 차이와 일치한다.**
커넥션을 얼마나 오래 잡느냐가 상한을 결정한다는 것이 숫자로 드러난다 —
**F-05(상품 목록 N+1)의 비용이 여기서 정량화된다.**

## 버린 구간

**초당 1,300 이후.** 배수가 70~96 으로 붕괴했고 `dropped_iterations` 도 이 구간에 몰렸다.
다만 **VM CPU 는 68% 로 폐기 기준(90%)에 닿지 않았다** — 2회차와 달리 호스트 포화가 아니라
앱이 밀린 것이라, 붕괴 자체는 앱의 거동으로 읽어도 된다. 절대 수치(배수 96 등)는 인용하지 않는다.

무릎 지점(초당 1,000~1,200)은 CPU 59~66 % 에서 관측됐으므로 **유효하다.**

## 자동 중단이 처음으로 값을 했다

배수 10배 초과 시 중단을 이 회차부터 걸었다. 2회차는 무릎을 넘긴 뒤 10분을 붕괴 상태로 돌아
그 구간을 통째로 폐기했는데, 이번에는 **붕괴 30초 만에 끝났다.** 시간도 아끼고 호스트 포화로
인한 오염도 없었다(CPU 최대 68%).

## 정리

`./setup/unload-write.sh` 로 `[load-write]` 를 삭제해 상품 10만 건 상태로 되돌렸다.
