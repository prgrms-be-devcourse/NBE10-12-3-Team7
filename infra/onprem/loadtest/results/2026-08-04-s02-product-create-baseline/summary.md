# 회차 요약 — s02-product-create / baseline (쓰기 1회차)

조건은 옆의 `conditions.md` 에 자동으로 남아 있다. 여기는 **그래서 무엇을 알게 됐는가**를 쓴다.

## 무엇을 확인하려고 돌렸나

지금까지(s01)는 전부 읽기였다. **쓰기가 몰릴 때 버티는가**를 처음 잰다.
층위 (a) — 등록 API 만 건다. 실제 화면은 이미지 업로드 → 등록 두 단계지만, 업로드를 섞으면
무릎이 나와도 DB 때문인지 RustFS 때문인지 구분할 수 없다.

## 결과 — 무릎이 없다. 그리고 부하 중이 무부하보다 빠르다

## 무릎

**이 계단에서는 안 꺾였다.** 아무것도 포화되지 않았다.

- **커넥션 풀 아님** — `pending` 전 구간 0, `active` 최대 2/10
- **락 경합 아님** — `innodb_row_lock_current_waits` 전 구간 0
- **CPU 아님** — 최대 39 % (읽기 1회차는 같은 도착률에서 61 %)

## 이 회차의 핵심 발견 — 이 앱은 쓰기가 아니라 읽기가 병목이다

같은 초당 600 도착률에서 읽기 회차와 비교하면:

| | 쓰기(등록) | 읽기(목록, 1회차) |
|---|---|---|
| 요청/초 | 600 | 1,200 (화면당 API 2건) |
| **MySQL QPS** | **5,403** | **22,200** |
| **요청당 쿼리** | **9.0** | **18.5** |
| VM CPU | **39 %** | 61 % |
| 배수 p95 | **0.75** | 1.17 |

**등록 1건이 만드는 쿼리가 조회 1건의 절반이다.** 등록은 상품 + 이미지 INSERT 인데
조회는 항목마다 쿼리가 붙는다(F-05, `size=30` 에서 33 쿼리).

중고거래 서비스에서 흔히 "쓰기가 무겁다"고 예상하지만 **이 앱은 반대다.**
읽기 경로의 N+1 이 그만큼 크다는 뜻이고, **F-05 의 우선순위가 한 단계 더 올라간다.**

## 데이터가 두 배가 되는 동안 느려지지 않았다

이 회차가 123,299 건을 만들어 상품이 **100,006 → 223,325** 가 됐다. 그런데 **응답은 오히려
빨라졌다**(14 ms → 6.2 ms). 워밍업 효과가 데이터 증가 효과를 압도했다.

INSERT 는 테이블이 커져도 비용이 거의 안 변한다 — 인덱스 트리 깊이가 로그로 늘 뿐이다.
**읽기와 대비되는 지점이다.** perf 의 F-01 은 조회가 데이터량에 26.7 배로 악화됐다.

## 측정 방법에 대한 메모 — 기준선이 낙관 쪽으로 치우친다

배수가 **0.75 로 1 보다 작다.** 부하 중 정상상태(6~7 ms)가 `setup()` 이 잰 무부하(10.0 ms)보다
빠르기 때문이다. 회차 전에 등록 150 건으로 외부 워밍업을 했는데도 그렇다 —
부하가 지속되면 JIT·커넥션이 더 최적화되는 것으로 보인다.

**기준선이 판정의 분모라서, 모든 회차의 배수가 실제보다 조금 좋게 나온다.** 허용선이 3 배라
결론이 뒤집힐 정도는 아니지만 무릎 위치를 논할 때 감안해야 한다. 개선하려면 부하를 조금 건
뒤에 기준선을 재거나 표본을 더 늘려야 한다 — **다음 회차의 검토 항목이다.**

## 버린 구간

없음. `dropped_iterations` 0, VM CPU 최대 39 % 로 폐기 기준(90 %)에 한참 못 미쳤다.

## 정리

회차 후 `./setup/unload-write.sh` 로 `[load-write]` 를 삭제해 상품 10만 건 상태로 되돌렸다.
다음 회차가 다른 데이터 크기에서 시작하지 않도록 하기 위해서다.

## 다음 회차의 목적

1. **층위 (b) — 이미지 업로드 + 등록.** 이번 회차는 `imageUrls` 에 저장소에 없는 문자열을

2. 쓰기가 이 계단에서 안 꺾였으므로 상한을 알려면 계단을 더 올려야 한다. 다만 초당 600 에서
   이미 회차당 12 만 건이 쌓이므로 **계단을 올리면 데이터 증가가 더 커진다** — 유지 시간을
   더 줄이거나 상한 탐색을 별도 회차로 분리하는 편이 낫다.
