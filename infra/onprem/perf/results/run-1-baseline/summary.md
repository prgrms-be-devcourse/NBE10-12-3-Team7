# 볼륨 테스트 — 2026-08-01

상품을 1만 → 50만 건까지 여섯 계단으로 누적 적재하며, **사람이 화면에서 실제로 부르는 API만**
재서 "어디까지 버티나"를 찾았다. 동시 요청을 올리는 부하 테스트가 아니라 볼륨 테스트다 —
부하는 낮게 고정하고 데이터량만 바꿨다.

## 조건

| 항목 | 값 |
|---|---|
| 대상 | 온프레미스 스택 (`infra/onprem`) |
| 버퍼풀 | 128 MiB (MySQL 기본값. 실험 내내 고정) |
| 부속 데이터 | 찜 10.3만 · 댓글 10.3만 · 알림 5.5만 · 신고 6만 (계단마다 재구성) |
| 테스트 계정 집중 | 찜 3,000 · 안읽음 3,000 · 신고 500 · 인기 상품 댓글 3,000 |
| 측정 | 워밍업 1회 버리고 7회, 중앙값. 관리자는 3회 |
| 실행 | `./scenarios/run-step.sh <계단> <목표 상품수>` |

계단마다 `step-N.json`(원시값)과 `step-N-grafana.png`(그 시점 대시보드)가 남아 있다.

## 결론 1 — 문제는 두 곳뿐이고, 성격이 다르다

여덟 개 중 여섯은 30배 데이터에도 **미동이 없다**(0.8~1.0배). 나빠진 것은 둘이고,
같은 "느려짐"이지만 곡선의 모양이 다르다.

### 동네 필터 — 무릎이 있는 비선형

계단 간 증가율을 보면 특정 지점에서 뒤집힌다.

| 구간 | 데이터 | 응답 | |
|---|---|---|---|
| 1만→3만 | 3.0배 | 1.58배 | 데이터보다 완만 |
| 3만→10만 | 3.3배 | 1.34배 | 여전히 완만 |
| **10만→20만** | **2.0배** | **3.61배** | **← 무릎** |
| 20만→30만 | 1.5배 | 1.89배 | 이후 계속 가파름 |
| 30만→50만 | 1.7배 | 1.84배 | 기울기 안정 |

**같은 구간에서 버퍼풀 히트율도 처음 꺾였다**(99.982 → 99.937). DB 139 → 211 MiB 로
버퍼풀 128 MiB 를 확실히 넘어선 지점이다. 원인과 결과가 같은 계단에 있다.

무릎 이후 기울기가 1.84~1.89배로 안정된 것은, 이 지점을 넘으면 **예측 가능하게 나빠진다**는
뜻이다. 50만에서 315ms 이므로 100만이면 600ms 대가 된다.

### 관리자 상품 목록 — 무릎이 없는 선형

계단 간 1.83 / 1.61 / 1.65 / 1.38 / 1.66배. 시종일관 데이터 증가율의 절반~비슷한 비율로 커진다.
캐시와 무관하고, 페이징이 없어 **응답 자체가 행 수에 비례해 커지기** 때문이다.
50만 건에서 6.5초, 응답 수백 MB.

## 결론 2 — 처방이 다르다

| | 동네 필터 | 관리자 상품 |
|---|---|---|
| 곡선 | 비선형 (무릎 있음) | 선형 |
| 원인 | 버퍼풀 초과 → 캐시 미스 | 페이징 없음 → 응답 크기 |
| 후보 처방 | 인덱스 / 버퍼풀 확대 | 페이징 도입 |
| 사용자 영향 | **주 경로** (동네 기반 서비스) | 관리자만 |

동네 필터는 부가 기능이 아니다. 동네 기반 중고거래에서 대부분의 사용자가 타는 경로다.

## 결론 3 — 잘 되어 있는 부분

목록 진입·스크롤·상세·댓글이 30배 데이터에도 12ms 안팎으로 평평하다. `id DESC LIMIT 30`
커서 페이징과 PK 조회는 전체 크기와 무관하게 상위 몇 건만 본다. **읽기 경로 설계가 제대로
작동하고 있다는 증거다.**

관리자 회원 목록도 평평하다(10.9 → 9.6ms). 페이징이 없지만 회원이 508명으로 고정이라서다.
**"페이징 없음"이 곧 위험은 아니고, 거기에 데이터 증가가 겹쳐야 문제가 된다.**

## 측정 방법에서 고친 것

실험 도중 기록이 통째로 틀린 적이 세 번 있었다. 전부 "조용히 틀린 숫자가 표에 남는" 유형이라
원인과 대응을 남긴다.

**① 요청 제한에 걸려 429 를 측정했다.** 대시보드에 신호를 남기려 초당 7~8건 트래픽을 동시에
흘렸는데 앱의 제한(10초당 60건)에 걸렸다. 거부 응답은 본문이 없어 빨리 돌아오므로 카테고리
응답이 260ms → 3.4ms 로 "빨라진" 것처럼 보였다. → `snapshot.sh` 가 HTTP 200 이 아니면
즉시 중단하도록 고쳤다. **스냅샷 중에는 다른 트래픽을 흘리지 않는다.**

**② 프로브 대상 id 를 하드코딩했다.** 계단마다 데이터를 지우고 다시 넣으면 id 가 바뀌어
404 가 났다. → 매번 DB 에서 현재 값을 찾도록 바꿨다.

**③ 측정 실패가 스크립트를 멈추지 못했다.** `$( )` 안의 `exit` 는 서브셸만 끝내서, 404 를
만나고도 빈 값으로 계속 진행해 기록을 남겼다. → 표식을 반환해 호출부가 중단하도록 고쳤다.

## 알려진 한계

- **절대 수치는 다른 환경과 비교할 수 없다.** Docker Desktop(macOS)은 컨테이너 네트워크가
  gvisor 유저스페이스를 거친다. 이 표는 **계단 간 비교**에만 쓴다.
- **계단 2 값에 노이즈가 있다.** 목록 진입 26.0ms, 스크롤 20.5ms 는 앞뒤 계단(13~14ms,
  13.5ms)과 어긋난다. 볼륨 효과로 설명되지 않으므로 측정 시점의 간섭으로 본다.
- **히트율이 마지막 계단에서 되레 올랐다**(99.905 → 99.942). 프로브가 같은 페이지를 반복
  조회해 분모가 커진 영향으로 보인다. 비율보다 **디스크 읽기 누계**가 더 정직한 신호다.
- **멀쩡한 여섯 개의 한계는 확인하지 않았다.** 구조상(상위 30건만 조회) 깨지지 않을 것으로
  보지만 300배 이상에서는 재보지 않았다.
- **화면 체감은 아직 기록하지 않았다.** 서버 315ms 가 사용자에게 어떻게 느껴지는지는
  `manual.md` 에 별도로 남긴다. 서버 시간과 체감은 다른 질문이다.
