# perf — 온프레미스 스택 성능 검증

데이터를 계단식으로 적재하며 **"어디까지 버티나"** 를 재는 자산이다. 동시 요청을 올리는 부하
테스트가 아니라 **볼륨 테스트**가 주다 — 부하는 낮게 고정하고 데이터량만 바꾼다.

## 왜 볼륨 테스트인가

이 호스트는 Docker Desktop(macOS)이라 컨테이너 네트워크가 gvisor 유저스페이스를 거친다.
동시 요청을 올리면 앱이 아니라 네트워크 계층이 먼저 왜곡을 만들어, 절대 수치를 믿을 수 없다.

볼륨 테스트는 부하를 낮게 유지한 채 데이터만 바꾸므로 네트워크가 병목에 닿지 않는다. 관측되는
변화가 거의 순수하게 DB·쿼리 특성이다. **이 환경의 약점을 우회하는 설계다.**

## 왜 여기(infra/onprem 아래)에 있나

바로 위 `../.env` 에 DB 비밀번호·Grafana 계정이 있다. perf 안에 비밀값을 복제하지 않고
`lib/common.sh` 가 그것만 읽는다. 자격증명이 두 군데 생기는 것을 막는다.

폴더 위치는 온프레미스지만 스크립트는 대상을 강제하지 않는다. env로 덮어쓰면 다른 지형에도 쓴다:

```bash
BASE_URL=http://192.168.0.10 MYSQL_CONTAINER=other-mysql ./scenarios/...
```

## 지금 있는 것

| 경로 | 역할 |
|---|---|
| `lib/common.sh` | 공통 헬퍼. `../.env` 로드, MySQL 실행, Prometheus 조회 |
| `dataset/` | 적재할 볼륨 데이터(SQL). **아직 비어 있다** |
| `probe/` | 측정용 k6 스크립트. **아직 비어 있다** |
| `scenarios/` | 계단 실행 절차. **아직 비어 있다** |
| `results/` | 측정 기록. 실행 단위 폴더로 쌓인다 |

> 이 표에는 **실제로 존재하는 것만** 적는다. 이전 loadtest/ 는 README가 스크립트 12개를
> 안내하는데 실제로는 8개뿐이어서 신뢰를 잃었다. 없는 파일을 미리 적지 않는다.

## 실행 전제

- 온프레미스 스택이 떠 있을 것 — `docker compose --env-file .env up -d` (상위 폴더)
- 관측 스택이 떠 있을 것 — `--profile observability`. 측정값을 Prometheus에서 읽는다
- `../.env` 가 채워져 있을 것

헬퍼가 잘 붙는지 확인:

```bash
bash -c 'source lib/common.sh; require_stack; echo "DB $(db_size_mib) MiB / 히트율 $(buffer_hit_rate)%"'
```

## 실험 설계

### 계단

| 계단 | 상품 | 예상 DB 크기 | 예상 사건 |
|---|---|---|---|
| 1 | 1만 | 약 10 MiB | 전부 메모리. **기준선** |
| 2 | 3만 | 약 30 MiB | 변화 거의 없어야 정상 |
| 3 | 10만 | 약 100 MiB | 버퍼풀(128 MiB) 경계 접근 |
| 4 | 20만 | 약 200 MiB | 히트율 하락 시작 예상 |
| 5 | 30만 | 약 300 MiB | 디스크 읽기 본격화 |

계단마다: **적재 → 30초 안정화 → 프로브 60초 → 기록**. 데이터는 **누적**한다(초기화하지 않는다).
실제 서비스도 쌓이는 방향이고, 조건을 맞춰야 하면 MySQL을 재시작해 버퍼풀을 비운다.

### 프로브

성격이 다른 세 쿼리를 **같이** 잰다. 하나만 재면 "느려졌다"로 끝나지만, 셋을 같이 재면
"인덱스를 타는 쿼리는 멀쩡한데 LIKE 검색만 무너졌다"가 나온다.

| 대상 | 쿼리 특성 |
|---|---|
| 상품 목록 (커서) | PK 정렬. 인덱스를 탄다 |
| 상품 검색 | `lower(title) LIKE '%kw%'` — **선행 와일드카드라 인덱스가 무용지물**. 주인공 |
| 카테고리별 목록 | FK 인덱스 |

프로브는 **재는 도구지 괴롭히는 도구가 아니다.** VU 5 수준으로 낮게 고정한다.

### 판정 기준

세 가지를 다 기록하되 **판정은 상대 악화로** 한다. 이 환경의 절대 수치는 비교용으로만 쓴다.

| 기준 | 값 |
|---|---|
| 상대 악화 (판정) | 1단계 p95의 3배 |
| 절대값 (참고) | p95 < 1초 |
| 버퍼풀 히트율 (관찰) | 99% 미만 진입 시점 |

히트율이 떨어지는 건 실패가 아니라 **예정된 관찰 포인트다.** 그 지점이 나와야 실험이 성공한 것이다.

## 지금 하지 않는 것

의도적으로 미룬다. 부하테스트가 필요성을 증명한 뒤에 손대야 개선 효과를 말할 수 있다.

- **인덱스 추가** — `products` 에 검색용 인덱스가 없는 것은 결함이지만 지금은 그대로 둔다
- **버퍼풀 확대** — 128 MiB 기본값 유지. 3단계에서 넘치는 것을 보고 나서 올린다

## 규칙

1. **README는 존재하는 파일만 나열한다.** 계획은 아래 "앞으로" 절에 분리해 적는다
2. 실행 안내는 **macOS/Linux 기준**으로 적는다 (이전 loadtest/ 는 PowerShell 기준이라 못 썼다)
3. 계정·비밀값은 **`../.env` 참조로만** 적는다. 값을 문서에 쓰지 않는다
4. 결과는 `results/<날짜>-<실험명>/` 에 실행 단위로 남긴다. 원시 로그는 커밋하지 않는다

## dataset/ 은 Flyway가 아니다

`dataset/` 의 SQL은 번호 접두사로 실행 순서를 표현하지만 **마이그레이션이 아니다.**
`backend/src/main/resources/db/migration/` 에 두면 운영 배포 때 실행되므로 **거기 두지 않는다.**
앱 이미지 밖, 이 폴더에만 존재한다.

앱의 시더(`global/init` 의 마스터·부트스트랩·데모)와도 다른 것이다. 그쪽은 앱이 기동할 때
넣는 데이터고, 여기는 실험용 볼륨이다. 그래서 이름도 `seed/` 가 아니라 `dataset/` 이다.
