# FINDINGS — 성능 문제 대장

> 상위: [README.md](README.md) · [../README.md](../README.md) · [../../infra.md](../../infra.md)
> 근거가 되는 회차 기록: [results/](results/) (볼륨) · [../loadtest/results/](../loadtest/results/) (부하)

회차를 관통하는 문서다. `results/run-N-*/summary.md` 는 그 회차의 결론이고, 여기는
**문제 하나를 발견부터 해결까지 따라가는 곳**이다.

각 항목의 **검증** 줄이 다음 회차의 목적이 된다. 그게 없으면 매번 "뭘 확인하려고 돌리지?"를
다시 정해야 한다.

## 상태 표기

| 표기 | 뜻 |
|---|---|
| 미해결 | 원인 가설만 있고 손대지 않았다 |
| 개선중 | 처방을 적용했으나 아직 재측정하지 않았다 |
| 해결 | 재측정으로 확인했다. 근거 숫자를 함께 적는다 |
| 부분해결 | 나아졌으나 목표에 못 미쳤다 |
| 보류 | 의도적으로 미룬다. 이유를 적는다 |

## F-01 · 동네 필터가 버퍼풀 초과 후 급격히 느려진다

- **상태**: 미해결
- **영향**: 사용자 주 경로. 동네 기반 중고거래에서 대부분이 타는 화면이다
- **증상**: `GET /api/products?size=30&regionCodes=..` 11.8 → 315.0 ms (26.7배)
- **근거**: `run-1-baseline`. 계단 간 증가율이 1.58 / 1.34 / **3.61** / 1.89 / 1.84배로
  10만→20만 구간에서 뒤집힌다. **같은 구간에서 버퍼풀 히트율도 처음 하락**(99.982 → 99.937).
  DB 139 → 211 MiB 로 버퍼풀 128 MiB 를 넘어선 지점이다
- **가설**: `regions` 조인 대상 페이지가 버퍼풀에서 밀려나 캐시 미스가 발생한다.
  해당 동네 상품이 2.5만 건인데 그중 최신 30건을 찾는 과정에서 훑는 양이 크다
- **처방 후보**
  - (a) 복합 인덱스 추가 — `products(region_id, id)` 같은 형태로 정렬까지 인덱스로 해결
  - (b) 버퍼풀 확대 — 128 MiB 는 MySQL 기본값이다. VM 에 7.75 GiB 중 5 GiB 가 논다
  - (c) 쿼리 구조 변경 — `regions.code LIKE 'prefix%'` 조인 대신 지역 id 집합을 미리 구함
- **검증**: 같은 계단(1만~50만)으로 재측정. **10만→20만 구간 기울기가 2배 아래로**
  내려가면 해결. 20만·30만 절대값도 함께 본다
- **주의**: (a)와 (b)를 동시에 적용하면 무엇이 효과였는지 모른다. **한 번에 하나만** 바꾼다
- **동시성 축에서도 확인됨** (`loadtest/results/2026-08-04-s01-arrival-region-filter`):
  같은 동네 필터가 무부하에서 2.18배(8.2 → 18.0 ms)이고, 도착률을 올리면 **초당 200~230 진입**
  에서 무릎이 생긴다. 필터 없는 1회차는 600 진입까지 무릎이 없었다 — **상한이 3분의 1 이하로
  깎인다.** 다만 그 무릎의 직접 원인은 버퍼풀이 아니라 **커넥션 풀 고갈**이었다(히트율 100%
  유지, pending 0→187). 데이터량 축의 F-01 과 **메커니즘이 다르므로** 처방도 나뉠 수 있다

## F-02 · 관리자 상품 목록에 페이징이 없다

- **상태**: 미해결
- **영향**: 관리자 화면. 매일 쓰는 화면이고 데이터가 계속 늘어난다
- **증상**: `GET /api/admin/products` 589 → 6,542 ms (11.1배). 50만 건에서 응답 수백 MB
- **근거**: `run-1-baseline`. 계단 간 1.83 / 1.61 / 1.65 / 1.38 / 1.66배 — **무릎이 없는 선형**.
  F-01 과 달리 캐시와 무관하고, 행 수에 비례해 응답 자체가 커진다
- **가설**: `AdminProductService` 가 `findAll()` 로 전부 불러와 그대로 반환한다.
  관리자 컨트롤러 7개가 모두 같은 구조다
- **처방 후보**
  - (a) 페이징 도입 — 근본 해결이지만 프론트 화면도 함께 고쳐야 한다
  - (b) 반환 필드 축소 — 목록에 불필요한 본문·설명을 빼면 응답이 크게 준다. 임시방편
- **검증**: 같은 계단으로 재측정. 50만 건에서 **1초 미만 + 응답 1 MB 미만**이면 해결
- **참고**: 같은 구조인데 `GET /api/admin/members` 는 평평하다(10.9 → 9.6 ms).
  회원이 508명으로 고정이라서다. **페이징 없음이 곧 위험이 아니라, 데이터 증가가 겹쳐야
  문제가 된다.** 회원이 늘기 시작하면 같은 길을 간다

## F-03 · 관리자 신고 목록에 N+1 이 의심된다

- **상태**: 미해결
- **영향**: 관리자 화면
- **증상**: `GET /api/admin/reports` 가 **13.2 MB 를 8.7초**에 반환한다.
  같은 시점 `GET /api/admin/comments` 는 **18.3 MB 를 0.5초**에 반환했다 — **더 작은데 16배 느리다**
- **근거**: 상품 50만·신고 6만 적재 직후 실측 (2026-08-01, `run-1-baseline` 데이터셋 기준)
- **가설**: `AdminReportService` 가 `findAll()` 로 신고를 전부 불러온 뒤 대상 회원 id 를 모아
  다시 조회한다. 그 재조회가 건별로 풀리고 있는 것으로 보인다.
  **크기가 아니라 쿼리 횟수 문제다** — F-02 와 원인이 다르다
- **처방 후보**
  - (a) 대상 회원을 `IN` 절로 한 번에 조회
  - (b) 조인으로 한 쿼리에 해결
- **검증**: 같은 신고 건수에서 재측정. **응답 크기 대비 시간이 `admin_comments` 수준**
  (MB 당 30ms 안팎)이 되면 해결
- **아직 안 한 것**: 실제 쿼리 횟수를 세지 않았다. 정황 증거다.
  `EXPLAIN` 이나 쿼리 로그로 확인해야 가설이 확정된다

## F-04 · 관리자 대시보드 집계가 조용히 커진다

- **상태**: 보류 — 절대값이 아직 작다
- **증상**: `GET /api/admin/dashboard` 23.7 → 76.4 ms (3.2배)
- **근거**: `run-1-baseline`. `COUNT(*)` 5회를 도는 구조라 행 수에 정직하게 비례한다
- **보류 이유**: 76 ms 는 아직 체감되지 않는다. 다만 **100만 건이면 150 ms, 500만이면 750 ms**
  가 된다. F-01·F-02 를 먼저 처리하고 나서 본다
- **검증**: 볼륨을 더 올렸을 때 선형이 유지되는지 확인

## F-05 · 상품 목록에 N+1 이 있다 (항목 1건당 쿼리 1건)

- **상태**: 미해결
- **영향**: **사용자 주 경로.** 비로그인·로그인 모두 이 화면부터 진입한다
- **증상**: 응답 1건이 만드는 MySQL 쿼리 수가 **항목 수에 비례**한다

  | 요청 | 쿼리 |
  |---|---|
  | `GET /api/products?size=1` | 10 |
  | `GET /api/products?size=10` | 19 |
  | `GET /api/products?size=30` | **33** |
  | `GET /api/categories` | 9 |

  고정비 약 9건 + **항목당 약 0.8건**. 기울기 (33−10)/(30−1) ≈ 0.79.
- **근거**: `loadtest/results/2026-08-04-s01-arrival-baseline`. 부하 중 비율이 계단 전체에서
  일정했다 — 초당 20 진입에서 742 QPS, 600 진입에서 22,200 QPS, 양쪽 다 **요청당 18.5건**.
  exporter 몫이 무의미해지는 고부하에서도 비율이 같아 배경 잡음이 아니다.
  직접 측정(`show global status like 'Queries'` 전후 비교)으로 위 표를 확인했다.
- **왜 지금까지 안 보였나**: 부하테스트 내내 **버퍼풀 히트율이 100.000%** 였다. 33개 쿼리가
  전부 메모리 히트라 각각 0.1ms 수준이고, 응답 p95 는 9.9ms 로 오히려 빨랐다.
  **쿼리가 많다는 사실 자체는 응답시간에 드러나지 않는다.**
- **비용을 내는 축이 둘이다** (2회차 실측으로 갱신)

  | 축 | 메커니즘 | 근거 |
  |---|---|---|
  | 데이터량 | 캐시 밖으로 나가면 디스크 33번 | F-01 (히트율 하락과 상관) — **가설** |
  | **동시성** | **커넥션 점유 시간이 길어져 풀이 마른다** | `2026-08-04-s01-arrival-region-filter` — **실측** |

  등록 당시 "캐시 밖으로 나가면 터진다"만 가설로 적었는데, **동시성 축에서는 캐시와 무관하게
  터진다**는 것이 2회차에서 확인됐다. 동네 필터를 걸고 도착률을 올리자 초당 200~230 진입에서
  무릎이 생겼는데, 그때 **버퍼풀 히트율은 100.000% 를 유지**했고 `hikaricp_connections_pending`
  이 0 → 187, `active` 가 풀 최대(10)에 붙었다. VM CPU 는 57% 로 여유가 있었다.
  쿼리 33개가 전부 메모리 히트여도 **그동안 커넥션 하나를 계속 붙잡는다** — 동시성이 올라가면
  이것만으로 풀이 마른다.
- **처방 후보**
  - (a) 연관 엔티티를 `@EntityGraph`·fetch join 으로 한 번에 가져오기
  - (b) 목록 응답에 필요한 필드만 담은 projection 으로 조회
  - (c) 배치 조회(`@BatchSize`) — 항목당 1건을 페이지당 1건으로 줄인다
- **검증**: 같은 요청의 쿼리 수가 항목 수와 무관하게 고정되는지 (`size=30` 에서 10건 근처).
  그다음 둘 다 확인한다 — **동시성 축**: `s01-arrival` 을 동네 필터로 재실행해 무릎이 초당
  200~230 진입보다 뒤로 밀리는지. **데이터량 축**: F-01 의 사다리를 다시 돌려 10만→20만 구간
  기울기가 내려가는지
- **주의**: F-01 의 처방(인덱스·버퍼풀)과 **동시에 적용하지 않는다.** 무엇이 효과였는지
  구분되지 않는다
- **먼저 할 것 — 원인 확정이 처방보다 앞선다**: 커넥션 풀을 10 → 20~30 으로 올리고 같은
  계단을 재실행한다. 무릎이 뒤로 밀리면 "풀 고갈이 무릎의 원인"이 확정되고, 안 밀리면
  다른 것을 보고 있었다는 뜻이다. 설정 한 줄이라 되돌리기 쉽다.
  (2026-08-04 시도했으나 초당 100 진입에서 중단돼 미완 —
  `loadtest/results/2026-08-04-s01-arrival-pool-20/`. **쓰기 계단으로 검증하는 편이 낫다** —
  쓰기는 무릎이 초당 1,000~1,200 이라 계단 여유가 크다.)

### 비용이 얼마인지 — 쓰기와 대비하면 나온다

`loadtest/results/2026-08-04-s02-product-create-ceiling-1400` 에서 **쓰기 상한**을 쟀다.
같은 앱, 같은 커넥션 풀 10 개인데 무릎 위치가 5 배 차이난다:

| | 읽기(동네 필터) | 쓰기(상품 등록) |
|---|---|---|
| 무릎 | 초당 200~230 | **초당 1,000~1,200** |
| 요청당 쿼리 | 18.5 (목록 단독 33) | **9.0** |
| 무릎 시점 pending / active | 0→187 / 10 고정 | 0→186 / 10 고정 |
| 무릎 시점 VM CPU | 57 % | 68 % |

**두 시나리오가 독립적으로 같은 실패 서명을 냈다**(pending 급증 + active 풀 최대 고정 +
CPU 여유). 그리고 무릎 위치 차이의 방향이 요청당 쿼리 수 차이와 일치한다 —
**커넥션을 얼마나 오래 잡느냐가 상한을 결정한다.** 조회가 등록만큼만 쿼리를 쓴다면
읽기 상한도 크게 올라갈 여지가 있다는 뜻이다.

## 이 대장의 범위 밖 (잊지 않기 위해 적어둔다)

성능 문제가 아니라 여기서 추적하지 않지만, 실험 중 발견돼 미해결로 남아 있다.

- ~~**관리자 계정이 소스에 하드코딩돼 있다**~~ — ✅ **해결** (`fix/seed-admin-credentials`).
  `AdminSeeder` 가 `@Profile("!test")` 라 운영에서도 돌았고, `admin@dongnemarket.com` / `admin1234!`
  가 public 리포에 평문으로 있었다. `@Profile("dev")` + `APP_SEED_ADMIN` 스위치로 좁히고
  비밀번호를 `APP_SEED_ADMIN_PASSWORD` 로 뺐다. 운영 관리자는 수동 생성한다
  (`infra/infra.md` '관리자 계정').
  ⚠️ **git 히스토리에는 옛 비밀번호가 남아 있다.** 이 값을 쓴 계정이 배포돼 있었다면
  비밀번호 변경·계정 삭제가 별도로 필요하다 — 코드 수정만으로는 회수되지 않는다
- **프론트가 받아온 페이지 안에서만 필터링한다** — 카테고리 탭·검색창이 서버를 부르지 않고
  이미 받은 배열을 거른다(`products/page.tsx`). 상품이 50만인데 첫 페이지 30건만 받은
  상태에서 "의류" 탭을 누르면 **그 30건 중 의류만** 나온다. 성능이 아니라 기능이 어긋나는
  지점이라 부하테스트로는 안 잡힌다
- **Flyway 마이그레이션 누락** — `auctions`·`escrows`·`manner_scores` 가 V1~V6 에 없어
  온프레미스가 `ddl-auto=update` 로 우회 중이다(`infra/infra.md` 스키마 절 참고)
